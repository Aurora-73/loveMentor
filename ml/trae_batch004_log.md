## Step 2: 清洗 — clean_subset.py

### 2.1 分析可清洗的水印

在 Trae 可用的 `clean_subset.py` 范围内（纯字符串操作，无正则），我能清洗的：

| 样本 | 问题 | 清洗方式 |
|------|------|---------|
| s_003176 | `已读` 叠加（7处） | `--remove "已读"` |
| s_003176 | `4G@` 叠加行（2处） | `--drop-line "4G@"` |
| s_003176 | `0.07km1小时前` 行内叠加 | `--drop-line "0.07km"` |
| s_003176 | `始聊天了。` 片段 | `--drop-line "始聊天了"` |
| s_003176 | `消息轻熟女资料` 广告 | `--drop-line "消息轻熟女"` |

| s_003776 | `微信(4)` 叠加 | `--remove "微信(4)"` |

**思考**：这些操作会不会误伤其他干净样本？
- `--remove "已读"` — 其他 19 个样本中无正常聊天使用"已读"的，安全
- `--drop-line "年11月"` — 其他样本无提及"年11月"的，安全
- `--remove "微信(4)"` — 其他样本无此字符串，安全

但 `s_003176` 还有个问题：`我没妹0.07km1小时前` — 用 `--drop-line "0.07km"` 会删除整行，"我没妹"也被删了。这就是字符串操作的局限——我无法精确删除"0.07km1小时前"保留"我没妹"。决定接受这个损失（"我没妹"意思不太完整，删了影响不大）。

还有 `s_003176` 里的 `已读sorry` → 移除"已读"后变成 `sorry`，`已读你妹` → `你妹`。这些都是可理解的剩余内容，不影响。

### 2.3 --dry-run 结果分析

**发现问题：--dry-run 只显示消息数量的变化，不显示内容变化。**

### 4.2 提交体验 — 发现 Bug

第一次提交失败！只成功了第 1 条：

```
[OK] s_003019: 2|2|5|0|5|2|2|3|1|0
错误：需要 10 个分数或 -1:理由（放弃），收到 1 个
```

**原因**：`label_batches.py` 的 `--submit` 参数解析有 bug——它用 `sys.argv[submit_idx + 1:]` 取第一个 `--submit` 之后的所有参数，但中间夹着的 `--submit` 字符串也混进了分数列表。第 2 次迭代把 `--submit` 本身当分数解析，`"submit".split("|")` = `["submit"]` = 1 个元素 → 解析失败。

**修复**：过滤掉以 `--` 开头的字符串：
```python
score_args = [a for a in sys.argv[submit_idx + 1:] if not a.startswith("--")]
```

修复后重新提交（s_003019 已标注，剩余 19 条），全部成功：

```
[OK] s_003052 ~ s_003334: 全部 19 条成功
batch_004 进度: 550/1000 (55.0%)
```

### 4.3 发现第二个显示 Bug

提交完成后的进度显示：
```
进度: 550/13767 (4.0%)
```

`550` 是 batch_004 的已标注数，但分母 `13767` 是全部批次的总样本数——分子分母不对齐。

**修复**：改为显示批次级进度：
```python
batch_total = len(samples)
batch_done = len(done) + len(batch)
print(f"\nbatch_{batch_num} 进度: {batch_done}/{batch_total} ({batch_done / batch_total * 100:.1f}%)")
```

### 4.4 进度检查

```

总计: 11181/13767 (81.2%)
```

一轮完成：530 → 550 (+20)。

## 本轮反思

### 流程耗时

| 步骤 | 操作 | 时长 |
|------|------|------|
| 预览 | `read_for_label.py --offset 0 --count 20` | ~2s |
| 水印识别 | 人工浏览 20 个样本，标记问题 | ~2min |
| dry-run | `clean_subset.py --dry-run` + 结果分析 | ~3s + 30s |
| 实际清洗 | `clean_subset.py`（去掉 --dry-run） | ~1s |
| 验证 | 再次预览确认清洗效果 | ~2s |
| 标注 | 20 个样本 × 10 标签评分 | ~5min |
| 提交 | `label_batches.py --submit` | ~2s |
| **总计** | 一轮 20 条 | **~8min** |

### 脚本层面发现的问题（本轮修复）

| # | 问题 | 文件 | 严重程度 |
|---|------|------|---------|
| 1 | 多 `--submit` 时参数解析错误，`--submit` 字符串混入分数列表 | `label_batches.py` | **Bug — 阻断提交** |
| 2 | 提交后进度显示分子分母不对齐（批次级 vs 全局） | `label_batches.py` | Bug — 显示误导 |
| 3 | `--dry-run` 只报告消息数量变化，不报告内容修改 | `clean_subset.py` | 体验问题 |

### 有待改进的点

#### 1. clean_subset.py --dry-run 应该报告内容修改

当前 dry-run 只显示消息数的增减，不显示内容被修改了多少条。比如 s_003176 的 `已读` 被清除了，但所有消息都有剩余内容，消息数不变，dry-run 报告"无变化"——误导性强。

**改进方向**：dry-run 逐样本报告"X 条消息内容被修改，Y 条消息被删除"。

#### 2. read_for_label.py 和 clean_subset.py 的 offset 含义一致但容易混淆

两个脚本都用 `--offset` + `--count`，且都是从未标注列表中定位。概念一致，但用户必须先跑一次预览才知道 offset 对应哪些样本。

**改进方向**：在 clean_subset.py 的 dry-run 输出中显示样本 ID（已实现逐条显示 ID 和变化），但预览只显示 20 条的 offset=0。

#### 3. 预览–清洗–标注三步切换

每一步需要切换脚本（read_for_label → clean_subset → label_batches）。如果水印不止一种模式，需要在预览和 clean_subset 之间反复切换。

**改进方向**：统一编排脚本，把"预览→清洗→标注"三步合成一条命令。

#### 4. 清洗参数的长命令行

本次清洗用了 7 个参数：
```
--remove "已读" --remove "微信(4)" --drop-line "4G@" --drop-line "0.07km"
--drop-line "始聊天了" --drop-line "消息轻熟女" --drop-line "年11月"
```

如果水印模式更多，命令会更长。而且这些参数是手动从预览结果中逐条提取的。

**改进方向**：
- 支持从文件读取清洗规则
- 或 `clean_watermarks.py` 的全局水印模式覆盖更多场景（减少 Trae 手动清洗的需求）

#### 5. WCD 混合型水印无法用字符串操作处理

s_003176 的 `我没妹0.07km1小时前`——水印和正常内容混在一起，`--drop-line "0.07km"` 会删除整行，"我没妹"也被删了。

**限制**：`clean_subset.py` 只有字符串替换和行删除操作，没有正则。`clean_watermarks.py`（Dev 工具）有正则但 Trae 不能用。
